# OpenMIPS Cache Attributes and MMIO Mapping — RTL Review

**Status:** Source-level mapping review; no adapter RTL added.
**Reviewed repository:** [grantae/OpenMIPS](https://github.com/grantae/OpenMIPS)
**Files:** `hardware/src/MIPS32/Core/CPZero.v`, `hardware/src/MIPS32/Core/Processor.v`, `hardware/src/MIPS32/Core/MIPS_Defines.v`, and `hardware/src/MIPS32/Cache/DCache/DataCache_2KB.v`.

## Confirmed signal path

The inspected RTL shows this path:

1. `CPZero.v` assigns `M2_Cache = TLB_Cache_D` and `M2_PFN = TLB_PFN_D`.
2. `Processor.v` exports `DataMem_CacheAttr = M2_Cache`, `DataMem_PAddress = M2_PFN`, and `DataMem_PAddressValid = M2_PFN_Valid & ~W1_Flush_Pending`.
3. `DataCache_2KB.v` treats `CacheAttr_C == 3'b010` as uncacheable and chooses a word read for an uncacheable fill, rather than a cache-line read.
4. `MIPS32.v` carries that data-cache memory interface to the top-level `DataMem_*` pins.

Thus the uncacheable attribute is delivered by the translation/cache-attribute path; it is not automatically generated by the LOT fabric or by a standalone address decoder in the LOT adapter.

## Consequence for integration

**A physical-address range check alone is insufficient to prove that an access will be uncacheable.** The target program and the core's translation/privilege configuration must cause the intended MMIO address to arrive with the expected cache attribute. The physical address, cache attribute, valid indication, read/write command, byte enables, and response timing must all refer to the same accepted request.

Do not hard-code a final LOT MMIO base address yet. The project owner must choose the physical address map and memory controller topology. A candidate address range must be checked for overlap with RAM, reset/exception vectors, and any existing peripheral map.

## Remaining design questions

- How is the OpenMIPS TLB initialized for the boot/test program, and which address segment/configuration is used for MMIO?
- Which `EntryLo.C`/cache-attribute values are supported and how are they programmed for the test mapping?
- Does the integration use a TLB-mapped address or a direct-mapped segment, and what physical address reaches `DataMem_Address`?
- How are word address bits and `DataMem_Offset` interpreted by the external memory model?
- Does the LOT request/response path support byte enables? If not, must the adapter implement read-modify-write (which may be unsafe for side-effecting MMIO registers) or explicitly restrict the initial test to aligned full-word operations?
- How should unmapped LOT addresses behave when the core's exposed top-level memory interface has no explicit bus-error input?

## Next implementation scope

Before adding adapter RTL, define a **test-only memory map and boot configuration**. Keep normal memory and cache-line traffic on the RAM model. For the first test, use only aligned, full-word, uncacheable MMIO reads/writes to a behavioral LOT endpoint. Add byte/halfword and unmapped-address behavior only after the existing byte-enable and error contracts are settled.

## Validation boundary

These are source-level observations, not an executed OpenMIPS build or CPU-to-LOT integration. No processor RTL was copied into the LOT repository, no adapter was implemented, and no new simulator tests were run. Preserve the current 12-test LOT regression as the baseline.
